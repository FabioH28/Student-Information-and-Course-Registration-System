CIS — Campus Information System Requirements Specification

This document defines the intended production-ready scope for the Campus Information System (CIS), a role-based web platform that supports academic operations, student services, finance, campus communications, and institutional administration through a React frontend, FastAPI backend, and relational SQL data layer.

Project Title CIS — Campus Information System
Delivery Context Web-Based Multi-Role University Platform
Technology Baseline React, FastAPI, MySQL/MariaDB
Revision Date 12 April 2026

1. System Overview

CIS is intended to function as a centralized campus operations platform. It consolidates user identity, academic administration, registrations, attendance, grade management, finance operations, campus clubs, announcements, events, and student-facing service interactions into a single controlled environment.

Primary Objective Provide a secure and extensible institutional platform that reduces operational fragmentation and offers consistent workflows for students, teachers, and administrators.
Scope Boundary The system covers internal campus processes and excludes external payment gateways, external LMS grading tools, and public admissions portals unless explicitly integrated later.

2. Stakeholders and Actors

The platform is shaped around a role-based operating model. Each actor interacts with CIS according to institutional authority, data ownership, and operational responsibility.

Actor Description Core Responsibilities Primary Access Scope
Student Registered learner using the portal for self-service academic and service operations. View profile, register courses, review timetable, read inbox, inspect grades, review finance, join clubs. Own records only
Teacher Academic staff member responsible for instructional delivery and course-level records. Manage attendance, gradebooks, course rosters, academic alerts, and course communication. Assigned offerings and related students
Administrator Institutional operator with broad authority across academic, finance, and governance workflows. Provision users, maintain academic structure, manage finance, publish notices, supervise data. Institution-wide
System Owner Institutional sponsor accountable for governance, compliance, and roadmap prioritization. Approve policy, validate acceptance criteria, oversee deployment and operational maturity. Governance and oversight

Access Control Institution-managed accounts, authenticated sessions, forced password change, and role-based access control.
Academic Operations Programs, courses, offerings, registration, timetable, attendance, grading, and progression controls.
Campus Services Finance, clubs, announcements, events, notifications, and student support interactions.

FR-014 The system shall allow administrators to publish announcements and events, and shall expose them to relevant student users. High News and events created by admins appear in student news views.
FR-015 The system shall allow students to browse campus clubs and submit join requests or event participation requests where permitted. Medium Join requests and event registrations are stored and reviewable.

FR-024 The system shall expose stable API endpoints for frontend consumption across authentication, academic services, finance, clubs, news, and notifications. High Frontend modules interact with backend routes rather than local mock data.

5. Non-Functional Requirements

Non-functional requirements define the quality envelope within which CIS must operate. These constraints are essential for institutional trust, continuity, and operational viability.

ID Category Requirement Target Position
NFR-001 Security All authenticated API calls shall require verified tokens and enforce server-side authorization checks. Mandatory
NFR-002 Security Passwords shall be stored only as secure hashes and never in reversible plaintext form. Mandatory
NFR-003 Security The platform shall provide login throttling or temporary lockout after repeated failed authentication attempts. Mandatory
NFR-004 Performance Typical dashboard and list views shall load within acceptable user-perceived latency under normal institutional usage. Target: sub-2s for common queries
NFR-005 Availability The system shall support planned deployment patterns that allow routine backup, restart, and recovery without data corruption. High priority
NFR-006 Data Integrity Relational constraints, identifiers, and transactional operations shall prevent duplicate or contradictory academic records. Mandatory
NFR-007 Auditability Security-sensitive and governance-sensitive actions shall be traceable through timestamped audit records. Mandatory
NFR-008 Usability The interface shall be role-appropriate, mobile-responsive, and understandable to non-technical institutional users. Mandatory
NFR-009 Accessibility The platform should align with accessible semantic structure, readable contrast, and keyboard-operable primary workflows. Target: WCAG-aligned practice
NFR-010 Maintainability The system shall be modular enough that frontend, backend, and database layers can evolve without wholesale rewrites. Mandatory
NFR-011 Scalability The architecture shall permit growth in users, records, and modules through conventional database and API scaling practices. Target: institution-scale growth
NFR-012 Interoperability The platform shall use stable REST-based API contracts and environment-driven configuration for deployment portability. Mandatory
NFR-013 Privacy Users shall only be able to view personally identifiable or academic information for which they are explicitly authorized. Mandatory
NFR-014 Reliability Validation failures and operational errors shall return predictable and understandable responses without exposing sensitive internals. Mandatory
NFR-015 Deployment The application shall support containerized or equivalent repeatable deployment for backend, frontend, and database services. Preferred baseline

6. Business Rules

Business rules provide enforceable governance constraints that shape user behavior, data integrity, and procedural consistency across the platform.

  • Accounts shall be created by administrators; self-registration is outside the current institutional scope.
  • Student identifiers and employee identifiers should be system-generated to avoid duplication and inconsistent formatting.
  • Students may only register for offerings that belong to accessible academic structures and satisfy prerequisite or policy rules.
  • Teachers may only manage attendance and grades for offerings explicitly assigned to them.
  • Published final grades shall be treated as authoritative academic outcomes unless superseded by approved administrative correction.
  • Finance holds may restrict downstream student actions such as registration if institutional policy requires it.
  • Announcements and events shall be attributable to an authorized publisher and carry publication metadata.
  • Notifications shall be linked to a recipient or recipient group and support status transitions such as unread, read, or archived.
  • Password reset and password change actions shall invalidate vulnerable session states where appropriate.
  • Critical user lifecycle operations shall leave auditable evidence in the system log.
These business rules are intended to be enforced primarily by the backend and database layers so that data integrity does not depend on frontend behavior alone.

8. Data and Reporting Requirements

Data architecture and reporting features must support operational accuracy, decision support, and institutional accountability.

  • The system shall maintain structured master data for departments, programs, terms, courses, and offerings.
  • The system shall preserve role-linked profile data for students, teachers, staff, and administrators.
  • The system shall maintain transactional records for registrations, attendance sessions, grade items, invoices, payments, and membership requests.
  • The system shall support dashboard-level aggregation for academic load, outstanding balances, engagement counts, and notice volume.
  • Reports should support filtering by term, department, role, status, and time range.
  • Administrative exports should be possible for academic and finance review processes.
  • Audit and security records should be queryable for incident review and governance checks.
  • AI chat history, if retained, should be subject to institutional policy, retention, and privacy controls.
Recommended core reporting outputs include enrollment summaries, attendance exceptions, grade distributions, receivables summaries, club participation counts, event activity summaries, and user status reports.

9. Assumptions and Constraints

These assumptions provide context for design decisions and help distinguish immediate delivery scope from future expansion opportunities.

Assumption A1 The institution remains the sole authority responsible for account creation and role assignment.
Assumption A2 The initial deployment targets a single campus or a logically unified institutional data boundary.
Constraint C1 The current solution depends on institutional SQL infrastructure and environment-based secret management.
Constraint C2 External integrations such as live email delivery and payment gateway settlement are deferred until later phases.
The platform should be treated as expansion-ready rather than feature-final. The architecture is expected to evolve toward deeper automation, stronger testing, and richer operational integrations without requiring a structural rewrite.

10. Acceptance Position

A production-ready CIS release should be accepted only when the platform satisfies both functional completeness and operational readiness expectations for a university-grade information system.

Acceptance Area Minimum Condition Readiness Level
Identity and Security Login, password change, password reset, lockout, audit logging, and role enforcement work reliably. Required
Academic Operations Admins can manage academic structures, teachers can manage teaching records, and students can complete registration and review outcomes. Required
Finance and Services Invoices, payments, holds, notices, clubs, events, and notifications operate through controlled backend workflows. Required
Operational Quality Validation, logging, backup posture, deployment repeatability, and baseline automated testing are in place. Must mature before launch
Future Enhancement Readiness The architecture supports continued expansion such as richer analytics, messaging, external integrations, and policy automation. Strategic objective
In academic project terms, this specification positions CIS as a professionally scoped enterprise information system with clear domain boundaries, traceable responsibilities, and a strong basis for further implementation, validation, and research-oriented evaluation.
